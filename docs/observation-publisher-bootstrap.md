# Zigbee observation setup on pairing and reconnect

The Hub reconciles paired registry identities against the current Zigbee2MQTT inventory and effective `bridge/info`. It derives observation properties from each readable, observable entity; neither room, category nor manufacturer selects them. Physical parents supply the values for their logical channels. Private-device permissions and cloud/analytics eligibility remain independently enforced.

For those identities only, the Hub applies the local publisher options `optimistic: false` and a union of existing `filtered_cache` filters with exact supported property names. It also ensures `advanced.last_seen: ISO_8601`. This uses the documented `bridge/request/device/options` and `bridge/request/options` APIs, verified on Zigbee2MQTT2.13.0. The installed API persists settings and publishes effective bridge info before replying. No device reporting configuration, polling, actuator request or radio restart is issued by this setup.

Discovery, bridge-info updates and the existing observation timer retry the reconciliation. One request is outstanding at a time, with a 30-second response window and a minimum 60 seconds between attempts for the same target. Successful configuration is idempotent. Reconnect drops runtime proof and rechecks it; requests do not run without current paired inventory. Unsupported restart-required configurations stay fail-closed and are reported as such in MQTT status.

Local YAML alone is insufficient evidence. A per-value timestamp requires effective timestamp/optimistic/cache settings, the exact local cache exclusion, a non-retained MQTT packet with a valid source UTC timestamp and an unambiguous endpoint/property binding. The first live packet after setup/reconnect is discarded to flush any old publisher cache. Its replays, older values, null placeholders, retained packets and missing/future timestamps never overwrite or renew a previously genuine observation.

After setup, readings appear only as the device genuinely reports them. The Hub does not backdate or promote a cached initial target, temperature or heating value. A device that never reports a supported attribute cannot supply it automatically. A reporting guarantee is a separate contract: these publisher settings alone do not mark readings current or turn heating demand into gas use. No extra reporting/polling policy is enabled.

References: [Zigbee2MQTT MQTT API](https://www.zigbee2mqtt.io/guide/usage/mqtt_topics_and_messages.html), [device options](https://www.zigbee2mqtt.io/guide/configuration/devices-groups.html). Cache transition behavior was independently checked in the installed2.13.0 `dist/state.js` and `dist/controller.js`: state.set returns the old merged state once while excluding the configured properties from its next cache.
